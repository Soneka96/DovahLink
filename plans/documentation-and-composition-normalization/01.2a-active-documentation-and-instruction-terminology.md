## Why this is a stable concept

This concept touches only active, present-tense documentation and instructions --
never public wire fields, never internal implementation identifiers, never historical
record. It can complete and merge without waiting on any decision about
`bridgeVersion`/`bridgeInstanceId` (that is `01.3a`'s job), and it must complete before
`01.2b` starts so internal renames read against already-corrected active documentation
rather than documentation still describing "Bridge" as current.

## Goal

Make all active, present-tense documentation and comment prose describe the current
Host + Adapter architecture accurately, regardless of which physical file type that
prose lives in. Documentation/comment-text-only. No runtime or wire behavior change.

## Scope rule: prose ownership is file-type-agnostic

Concept 01.2a owns active documentation and comment prose regardless of the physical
file type in which that prose lives. This includes Markdown, XML/Doxygen/Dart
documentation comments, ordinary explanatory source comments, Papyrus comments, YAML
comments, and equivalent documentation surfaces. A source file may be touched in
01.2a only for documentation/comment text -- identifiers, filenames, declarations,
signatures, executable statements, serialization, behavior, and public API shape
remain unchanged (that is 01.2b's or, for public wire vocabulary, 01.3a-c's
territory). For example,
`sdk/dart/dovahlink_client/lib/src/dovahlink_client.dart:274`'s
`/// @throws [DovahLinkProtocolException] if the bridge rejects authentication.`
belongs to 01.2a even though it is inside SDK source, because it is general
behavioral prose about the current architecture, not a wire-field-specific comment.

**Do not let the same occurrence belong to both this concept and another.** A comment
describing what "the bridge" does as an actor (accepts, rejects, restarts) in general
prose is category A, owned here. A comment documenting the semantics of the
`bridgeVersion` or `bridgeInstanceId` wire field specifically -- for example
`sdk/dart/dovahlink_client/lib/src/protocol/envelope.dart`'s
`/// The identity of the bridge instance that produced this message`,
`host/DovahLink.Host/Client/Protocol/HelloAckPayload.cs`'s
`bridgeVersion is a legacy wire-field name retained for protocol compatibility`, or
`host/DovahLink.Host/Identity/AdapterInstanceId.cs`'s comparison to "the old
single-process `bridgeInstanceId` concept" -- is category D and stays with
`01.3a`/`01.3b`/`01.3c`, since updating it coherently requires the same decision that
governs the field itself. A comment naming an internal Bridge-named identifier (for
example `adapter/runtime/adapter_task_marshaller.hpp`'s stale
`IBridgeCallbackRegistry` cross-reference, or anything inside the
`app/lib/features/connection/**` `BridgeEntity`/`BridgeListScreen` cluster) is
category B and stays with `01.2b`, since the comment cannot be fixed independently of
the identifier it describes.

## Design

- Audit at minimum: `AGENTS.md`, `README.md`, `PRODUCT.md`, `ARCHITECTURE.md`,
  `CONTRIBUTING.md`, `ai/context/common.md`, `ai/context/host/**`,
  `ai/context/adapter/**`, `ai/context/skse/**`, `ai/context/protocol/**`,
  `ai/context/integration/**`, `ai/context/tooling/**`, currently-active roadmap
  documents, repository-consistency tests encoding current terminology, and every
  source file identified as carrying category-A comment prose (see the scope rule
  above) -- a representative starting set from this session's inventory:
  `sdk/dart/dovahlink_client/lib/src/dovahlink_client.dart`,
  `dovahlink_connection_exception.dart`, `dovahlink_pairing_exception.dart`,
  `dovahlink_protocol_exception.dart`, and
  `internal/{authentication,pairing,reconnect,session}/*.dart`'s service-behavior doc
  comments ("negotiates trust with the bridge," "the bridge rejects authentication,"
  "the bridge restarted"). Re-verify this list at implementation time rather than
  trusting it as exhaustive.
- Classify every hit before editing (per D4's A-G categories); only category-A hits
  are in scope here, using the scope rule above to resolve file-type ambiguity. A hit
  is not touched merely because it contains "bridge" -- for example `AGENTS.md`'s
  "Bridge/Core" boundary line is category A and gets corrected to Host/Adapter/
  public-protocol/private-IPC language, but `ai/context/skse/architecture.md`'s
  "retired native Bridge" framing is category E and stays.
- `console-admin/dovahlink.yaml` and `DovahLinkAdmin.psc` cite a deleted
  implementation path (`bridge/game_state/commonlib_trust_admin_papyrus_adapter.cpp`)
  in currently-read console-command documentation -- update the path to its current
  `adapter/papyrus/commonlib_adapter_trust_admin_papyrus_adapter.cpp` location and the
  surrounding prose to current terminology.
- `roadmap/10-multi-bridge-and-local-discovery-foundation.md` (and any other still-
  `Planned` stage found to be in the same situation) names and describes *future,
  not-yet-built* work in terms of the retired Bridge -- this is category A, not
  historical E, since nothing has shipped under that name yet. Correcting a roadmap
  stage title/scope is more consequential than an ordinary doc fix; flag any such
  stage explicitly for maintainer confirmation before renaming rather than doing it
  silently, since `ai/context/common.md`'s "Numbering and history" rule requires a
  maintainer-approved scope for roadmap phase changes.
- Do not rename: `bridgeVersion`, `bridgeInstanceId`, any public SDK/API symbol tied
  to those fields, protocol fixtures carrying them, historically accurate released
  changelog entries, frozen source/reference material, archived/retired Bridge
  architecture (except to clarify it is historical where genuinely ambiguous), or any
  source-code identifier (`01.2b`'s job).
