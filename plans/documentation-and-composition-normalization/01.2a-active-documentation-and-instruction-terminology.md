never public wire fields, never internal implementation identifiers, never historical
record. It can complete and merge without waiting on any decision about
`bridgeVersion`/`bridgeInstanceId` (that is `01.3a`'s job), and it must complete before
`01.2b` starts so internal renames read against already-corrected active documentation
rather than documentation still describing "Bridge" as current.

## Goal

Make all active, present-tense repository instructions/documentation describe the
current Host + Adapter architecture accurately. Documentation/tooling-only. No
runtime or wire behavior change.

## Design

- Audit at minimum: `AGENTS.md`, `README.md`, `PRODUCT.md`, `ARCHITECTURE.md`,
  `CONTRIBUTING.md`, `ai/context/common.md`, `ai/context/host/**`,
  `ai/context/adapter/**`, `ai/context/skse/**`, `ai/context/protocol/**`,
  `ai/context/integration/**`, `ai/context/tooling/**`, currently-active roadmap
  documents, and repository-consistency tests encoding current terminology.
- Classify every hit before editing (per D4's A-G categories); only category-A hits
  in this file set are in scope here. A hit is not touched merely because it contains
  "bridge" -- for example `AGENTS.md`'s "Bridge/Core" boundary line is category A and
  gets corrected to Host/Adapter/public-protocol/private-IPC language, but
  `ai/context/skse/architecture.md`'s "retired native Bridge" framing is category E
  and stays.
- `console-admin/dovahlink.yaml` and `DovahLinkAdmin.psc` cite a deleted
  implementation path (`bridge/game_state/commonlib_trust_admin_papyrus_adapter.cpp`)
  in currently-read console-command documentation -- update the path to its current
  `adapter/papyrus/commonlib_adapter_trust_admin_papyrus_adapter.cpp` location and the
  surrounding prose to current terminology.
- `roadmap/10-multi-bridge-and-local-discovery-foundation.md` (and any other still-
  `Planned` stage found to be in the same situation) names and describes *future,
  not-yet-built* work in terms of the retired Bridge -- this is category A, not
  historical E, since nothing has shipped under that name yet. Correcting a roadmap
  stage title/scope is more consequential than an ordinary doc fix; flag any such
  stage explicitly for maintainer confirmation before renaming rather than doing it
  silently, since `ai/context/common.md`'s "Numbering and history" rule requires a
  maintainer-approved scope for roadmap phase changes.
- Do not rename: `bridgeVersion`, `bridgeInstanceId`, any public SDK/API symbol tied
  to those fields, protocol fixtures carrying them, historically accurate released
  changelog entries, frozen source/reference material, archived/retired Bridge
  architecture (except to clarify it is historical where genuinely ambiguous), or any
  source-code identifier (`01.2b`'s job).
