# Concept 01.3a -- Public vocabulary and identity/version semantics decision

**Status:** decided, pending implementation in `01.3b`/`01.3c`

**Covers:** No `SOURCE.md` requirement ID -- part of the D4 vocabulary-normalization
programme. See `DIVERGENCES.md` D4.

**Depends on:** Concept 01.2b merged to `main`.

## This is a design-only gate

**No wire implementation changes in this PR.** Its job is to resolve semantics before
anyone performs a public rename. `protocol/schema/README.md` already treats
`bridgeVersion` as a legacy wire-field name carrying the DovahLink product release
version; `ai/context/protocol/compatibility.md` already says the Host release
replaces the retired Bridge release as compatibility authority, and separately defers
the public authoritative-process instance identifier represented by the legacy
`bridgeInstanceId` field while explicitly prohibiting substituting `adapterInstanceId`,
a PID, a port, or a connection/session ID for it. This concept converts those
transitional notes into one complete, internally consistent decision.

## Mandatory decisions

### A. Compatibility authority

Decide exactly: what release/version a client compares against; whether the
authority is the Host release, the whole DovahLink product release, or another
existing source; the repository file/metadata source of truth; how the SDK declares
its supported range; too-old/too-new peer behavior; and confirm this remains a
release-compatibility check rather than a new protocol-generation number (the
protocol-generation model was already retired once, per
`ai/context/protocol/compatibility.md`'s history -- do not reintroduce it).

**Decision:** the compatibility authority is the Host release version, confirming
`ai/context/protocol/compatibility.md`'s already-recorded "Decided, not yet activated"
note rather than reopening it. Concretely: the Host's public wire contract (envelope
shape, message types, `hello`/`hello_ack` bootstrap) is what a client's declared
supported range is actually checked against, and the Host is the component that owns
and evolves that contract going forward -- Adapter's native IPC dialect to the Host is
a private internal detail, never itself compatibility-checked by a client. Source of
truth: the repository's single `VERSION` file, the same hand-maintained-literal-sync
mechanism `ai/context/common.md`'s Versioning section already governs (no new
versioning infrastructure); today this makes the Host's reported version numerically
identical to the whole-product number, because `VERSION` is still bumped once for
every language in the repo together. That is a current fact, not a permanent
guarantee -- the Host is free to diverge to its own release cadence in the future
without breaking this decision, since compatibility is scoped to what the Host itself
reports, not to whichever other component's number happens to currently match it. The
SDK continues to declare an explicit minimum/maximum supported range against this same
value (mechanism unchanged from today, only the label changes); too-old/too-new peer
behavior, and the fail-closed bootstrap check, are unchanged. This remains a
release-compatibility check, not a protocol-generation number -- no
`BootstrapProtocolV1`/`V2` is introduced.

**Finding for `01.3b`:** `host/DovahLink.Host/Client/Protocol/HelloAckPayload.cs`'s
current doc comment ("`bridgeVersion` ... carries the DovahLink product release
version, matching `adapter/vcpkg.json`'s `version-string`") describes the pre-decision
reading and contradicts this section's decision; `01.3b` corrects it to describe the
field as the Host's own release version, not a cross-reference to the Adapter's
`vcpkg.json`.

### B. Canonical version vocabulary

Decide exact names for: the wire field currently named `bridgeVersion`; the
Host-side property/model name; the Dart SDK/public model name; tests/fixtures; docs
terminology. Base the decision on semantics (does it carry a Host-only version or a
whole-product version?), not aesthetics -- do not choose `hostVersion` if it actually
carries a whole-product version, and do not choose `dovahLinkVersion` if
compatibility is explicitly owned by the Host release.

**Decision:** it carries the Host's own release version -- per Section A, compatibility
authority is explicitly owned by the Host release, so `dovahLinkVersion` is ruled out
by this concept's own guidance even though the number is numerically identical to the
whole-product version today. Exact names:

| Layer | Current | Decided |
| --- | --- | --- |
| Wire field (`hello_ack.payload`) | `bridgeVersion` | `hostVersion` |
| Host model (`HelloAckPayload`) | `BridgeVersion` | `HostVersion` |
| Host constant (`Constants`) | `PublicProtocolTransitionalBridgeVersion` | `PublicProtocolHostVersion` (drop "Transitional" -- the target name is decided, not a bridging label) |
| Dart SDK public model (`HelloResult`) | `bridgeVersion` | `hostVersion` |
| Dart SDK internal cache (`AuthenticationServiceImpl`) | `_bridgeVersion` | `_hostVersion` |
| Fixtures (`protocol/fixtures/**/*.json`) | `"bridgeVersion"` | `"hostVersion"` |
| Docs terminology | "Bridge version" / "Bridge release" | "Host version" / "Host release", except genuinely historical mentions of the retired native Bridge itself, which stay unchanged per `01.2a`/`01.2b`'s already-established convention |

`host/DovahLink.Host/Client/Protocol/CapabilityDescriptor.cs`'s deliberately-deferred
"independent of the Bridge/Host release version" phrasing (left ambiguous by `01.2b`
pending this decision) resolves to "independent of the Host release version."

### C. Public authoritative-process instance identity

Decide whether the public protocol exposes an instance identifier at all. If yes,
define: canonical name; owner; creation point; exact lifetime; stability across
client reconnects; behavior across Host restart; behavior on Adapter reconnect/
restart; relation to `playContextId`, `sessionId`, transport `ConnectionId`, and
`adapterInstanceId`; whether it may ever be null after Host startup; failure behavior
if generation fails; whether every Host-originated envelope carries it; how clients
cache/compare it; how state revision identity is scoped. It must not be a disguised
alias for `adapterInstanceId`, a PID, a port, a hostname, a socket, a connection ID,
or a session ID.

**Decision:** yes, the public protocol exposes one -- this is a hard gate for
`state_snapshot`/`state_event` publication, so "no" is not available.

**Core invariant:** `stateAuthorityId` identifies a Host authoritative-state
*continuity epoch*, not an Adapter process or a connection. If the revisions before and
after some event are not safely comparable -- the Host can no longer guarantee that an
old cached revision means the same thing as a new one -- `stateAuthorityId` MUST
change. If they remain safely comparable, it MUST NOT change. Every other bullet below
is a consequence of this one rule, not an independent list of process events to keep in
sync by hand; a future event this document doesn't enumerate is still governed by the
same test. Concretely, none of the following breaks continuity by itself, so none
rotates it: a `playContextId` change (a different axis, per the relation bullet below),
a new client session/reconnect/pairing/trust/revocation event (client-facing identity
and access are Host-owned but orthogonal to state-store continuity), or an
in-progress-but-not-yet-successful resync attempt -- rotation happens once the Host
actually establishes the new baseline, not when it merely starts trying to.

- **Canonical name:** `stateAuthorityId`. Deliberately not "instance" or "authority
  instance" -- the point of this identifier is continuity of the Host's in-memory
  authoritative state store, which is a narrower thing than either `adapterInstanceId`
  (native process identity) or the Host's own OS process identity (which
  `ARCHITECTURE.md`'s "Runtime and identity model" already says has no public
  identity), and a name echoing "instance" invites exactly the aliasing this decision
  must avoid.
- **Owner:** the Host -- it owns the one authoritative state store per play context
  (`ARCHITECTURE.md`'s "Authoritative state and revisions"), so it is the only
  component positioned to know when that store's continuity has actually been broken.
- **Creation point:** minted fresh (a new opaque value) at every event that breaks
  revision continuity per the core invariant above. Concretely, today's known trigger
  set is: Host process startup; a new `adapterInstanceId` binding (Adapter
  reconnect/restart); and **the same Adapter's IPC connection dropping and being
  re-established while both the Host process and the Adapter process stay alive** --
  `ai/context/host/architecture.md`'s "Host-to-adapter IPC contract" already requires
  the Host to treat that case as "adapter-sourced state unavailable" until a
  resynchronization handshake completes, and to treat the resynchronized result as "a
  fresh authoritative baseline, not an incremental update layered on stale state." That
  is precisely a continuity break with an unchanged `adapterInstanceId`, so tying
  rotation 1:1 to `adapterInstanceId` alone is insufficient -- it must also rotate here.
  It is not re-minted for a new client session, reconnect, or `ConnectionId` -- a
  socket-level event, alone, never breaks store continuity.
- **Why not `adapterInstanceId` itself:** two distinct continuity breaks do not change
  `adapterInstanceId`: (1) a Host restart while the underlying Adapter/Skyrim process
  keeps running, and (2) the same Adapter's IPC channel dropping and reconnecting
  without either process restarting. In both cases a client comparing only
  `adapterInstanceId` would wrongly treat reset/resynchronized Host-side state as
  continuous with what it had cached. Case (1) is exactly the scenario
  `ai/context/protocol/compatibility.md`'s existing "do not substitute
  `adapterInstanceId` ... for it" line already rules out; case (2) is the same class of
  bug the line's authors likely did not have in view, surfaced by re-reading
  `ai/context/host/architecture.md`'s already-documented IPC-loss/resync behavior
  against this decision.
- **Exact lifetime:** valid until the next continuity-breaking event per the core
  invariant; scoped to "this run of the Host's authoritative-state subsystem for its
  current binding," not to the Adapter's or the Host's raw process lifetime
  individually, and not 1:1 to `adapterInstanceId`.
- **Stability across client reconnects:** stable -- a new `sessionId`/`ConnectionId`
  is a socket-level event and never breaks store continuity by itself.
- **Behavior across Host restart:** changes (new value) -- the store resets, so any
  client-cached state under the old value must be treated as stale.
- **Behavior on Adapter reconnect/restart:** changes (new value) -- a new Adapter run
  always forces a fresh authoritative capture, which is a continuity break by
  definition.
- **Behavior on same-Adapter IPC loss and resync (no process restart on either side):**
  changes (new value) -- per the creation-point bullet above, this is a continuity break
  even though `adapterInstanceId` does not change.
- **Relation to `playContextId`/`sessionId`/`ConnectionId`/`adapterInstanceId`:**
  independent axis. `playContextId` narrows to which loaded save; `stateAuthorityId`
  narrows to which continuity epoch of the Host's state-authority subsystem produced
  it; `sessionId`/`ConnectionId` are per-socket and carry no state-authority meaning.
  `adapterInstanceId` remains a private Host-internal/IPC concept -- this decision does
  not expose it publicly. Every `adapterInstanceId` change forces a `stateAuthorityId`
  rotation, but not every `stateAuthorityId` rotation comes from an `adapterInstanceId`
  change (the IPC-loss/resync case above is the proof) -- the relationship is one
  direction only, not an alias.
- **May it ever be null after Host startup:** no. Fail-closed startup (an existing
  package-wide invariant) means the Host does not expose any externally reachable
  listener/admission path until it has successfully bound a value.
- **Failure behavior if generation fails:** Host startup fails closed -- same as any
  other fail-closed startup precondition; no new failure mode is introduced.
- **Exact wire presence:**

  | Message | `stateAuthorityId` |
  | --- | --- |
  | `hello_ack` | required, non-null |
  | `state_snapshot` | required, non-null |
  | `state_event` | required, non-null |
  | Any client-originated message | absent |
  | Any other Host-originated message (`pong`, pairing, errors, `capabilities`, ...) | absent |

  This is a closed list, not an example set -- a future Host-originated message adds
  itself to one side explicitly rather than being inferred as "every Host message"
  (`01.3c`'s own file previously used that looser phrasing; corrected there too).
- **Post-rotation baseline rule:** once `stateAuthorityId` changes, incremental
  revision continuity from the previous value is invalid outright. A client must
  receive a fresh `state_snapshot` establishing the new baseline before it may treat any
  subsequent `state_event` for that state area as incremental against it. A `state_event`
  arriving under a `stateAuthorityId` the client has not yet snapshotted is not a
  progressive update to apply -- it is a signal that a snapshot is still owed.
- **How clients cache/compare it:** opaque string equality, identical to how
  `bridgeInstanceId`/`playContextId` are already compared today -- no new comparison
  semantics.

### D. State and cache invalidation

Define the exact tuple determining whether cached authoritative state is from the
same authority/lifetime. The current tuple is
`(bridgeInstanceId, playContextId, stateArea)`
(`protocol/schema/README.md`'s "Registered state areas" section) -- state its exact
replacement and why, covering: same Host + reconnect; same Host + new session; same
Host + new play context; Host restart; Adapter reconnect; multiple concurrent
clients.

**Decision:** replace the tuple with `(stateAuthorityId, playContextId, stateArea)` --
same shape, `bridgeInstanceId` renamed/re-scoped to `stateAuthorityId` per Section C.

- **Same Host + reconnect:** tuple unchanged; client resumes from its cached revision.
- **Same Host + new session:** tuple unchanged -- a new session/`ConnectionId` carries
  no state-authority meaning, same as today.
- **Same Host + new play context:** `playContextId` changes; `stateAuthorityId`
  unchanged.
- **Host restart:** `stateAuthorityId` changes; every state area for every play context
  must be treated as stale regardless of `playContextId`.
- **Adapter reconnect (new `adapterInstanceId`):** `stateAuthorityId` changes, forcing a
  full resync.
- **Same-Adapter IPC loss and resync (no restart on either side):** `stateAuthorityId`
  changes too, per Section C's core invariant -- `adapterInstanceId` alone does not
  capture this continuity break.
- **Multiple concurrent clients:** all clients observe the same
  `(stateAuthorityId, playContextId)` pair at any given moment, since the Host owns one
  authoritative store shared across sessions (`ARCHITECTURE.md`'s "Session registry and
  delivery ownership") -- no per-client divergence in this tuple.

### E. Migration policy

State: is this intentionally breaking in the pre-release product (per
`ai/context/common.md`'s "Pre-release compatibility" -- the default answer is yes);
are old field names removed atomically; are aliases forbidden (default: yes); is any
temporary compatibility required (default: no); what SDK supported-range change is
required; how unsupported old clients fail. Default: do not invent compatibility
shims.

**Decision:** intentionally breaking, per `ai/context/common.md`'s "Pre-release
compatibility" default. `bridgeVersion`/`bridgeInstanceId` are removed atomically in
their respective implementation concepts, not deprecated or dual-named; no alias field,
no dual-write, no temporary compatibility shim. SDK supported-range change: the SDK
version that ships `01.3b`/`01.3c` bumps its declared minimum supported Host version to
the first Host release implementing this rename -- an old client built against the
`bridgeVersion`/`bridgeInstanceId` names simply fails the existing unknown-required-
field/incompatibility path already specified in `ai/context/protocol/compatibility.md`
("Incompatible combinations" and "Unknown data"); no new failure mode is introduced for
this migration specifically.
