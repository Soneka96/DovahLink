# Concept 01.3c -- Public authoritative-instance identity cutover

**Status:** pending

**Covers:** No `SOURCE.md` requirement ID -- part of the D4 vocabulary-normalization
programme. See `DIVERGENCES.md` D4. This concept, and `01.3b`, are the package's only
concepts permitted to change public/wire protocol behavior, and only to the exact
extent `01.3a` decides -- the approved exception to the package-wide "no protocol
change" invariant (`PLAN.md` section 3).

**Depends on:** Concept 01.3b merged to `main`.

## Goal

Implement exactly the public authoritative-process identity decision from `01.3a`.
This is an identity-lifecycle contract, not a variable rename -- treat it with the
same rigor `ARCHITECTURE.md`'s "Runtime and identity model" already applies to
`playContextId`/`clientId`/`sessionId`.

## Mandatory invariants to prove

Using the names `01.3a` chose: one identifier represents exactly one documented
authority lifetime; it is stable for that lifetime; it changes exactly at the
documented lifetime boundary; client reconnect does not accidentally create a new
authority identity; a new session does not accidentally create a new authority
identity; a play-context change does not masquerade as a Host restart;
`adapterInstanceId` remains semantically separate; PIDs/ports/paths/sockets are not
used as identity; multi-client sessions observe the same authoritative identity when
attached to the same authority; cache invalidation rejects data from an old
authoritative lifetime; state revision scope matches the canonical protocol document;
every required Host-originated message carries the decided value consistently; error
paths obey the schema; generation failure follows the exact `01.3a` policy.

## Required tests

At minimum, where applicable: same Host process + reconnect -> same authority
instance ID; same Host process + new authenticated session -> same authority instance
ID; same Host process + multiple concurrent clients -> same authority instance ID;
Host restart -> different authority instance ID; play-context change -> authority
instance ID unchanged, `playContextId` changes; cache holding
`(oldAuthorityId, old/newPlayContext, ...)` is rejected per the `01.3a` contract;
Adapter identity cannot be substituted for public authority identity; envelope
encode/decode across Host <-> SDK preserves the exact field; stale-state/recovery
tests use the new identity tuple; no residual active `bridgeInstanceId` contract use
remains unless `01.3a` explicitly retained it. Do not write tests that merely assert
a renamed string -- test lifecycle semantics.

## Files this concept may change

The files `01.3a`'s vocabulary table and blast-radius enumeration name, verified by
this concept's own re-run inventory: `protocol/schema/README.md`'s envelope/identity
sections, the ~57 `bridgeInstanceId`-carrying fixtures (nearly all of
`protocol/fixtures/`, since this field is in the standard envelope header), Host's
envelope/identity code
(`host/DovahLink.Host/Client/Protocol/PublicEnvelope.cs`,
`PublicEnvelopeCodec.cs`, and adjacent identity/availability tracking) and its tests,
the SDK's envelope/session/reconnect code and tests, `ARCHITECTURE.md`'s identity
model, and `ai/context/protocol/compatibility.md`'s "Deferred: public instance
identifier" section (no longer deferred once this merges).

## Non-goals

- Compatibility/version vocabulary -- already done in `01.3b`.
- Any decision not already made in `01.3a` -- if a gap is found, stop and return to
  `01.3a`.
- Any Host/Adapter composition or lifetime-ownership change -- Concepts 02/03,
  starting only after this merges.

## PR-size gate

Expected changed files: ~75-90 (large -- `bridgeInstanceId` appears in 57 of
`protocol/fixtures/`'s JSON fixtures plus Host/SDK envelope code, tests, and docs).
Hard stop: 100. Re-plan threshold: >80.

This is the concept in the D4 chain most likely to need a pre-planned split. If the
`01.3a`-informed re-run inventory predicts >80 files, split by fixture/consumer
family before implementation -- for example connection/pairing fixtures and their
Host/SDK consumers in one PR, state/subscription/error fixtures and their consumers
in a second -- never by arbitrary alphabetical range, and never such that either half
leaves `main` in a broken intermediate wire state (per D4's "never split a protocol
migration into a broken intermediate state" rule: if an atomic migration cannot be
safely split, stop for maintainer review rather than inventing a dual-field/alias
compatibility shim to force it under the limit).

## Completion criteria and evidence

- `01.3a`'s identity decision is implemented exactly.
- Canonical protocol docs and runtime agree; cache/revision/recovery semantics agree.
- Relevant Host, SDK, integration, and app tests are green.
- No accidental Adapter coupling.
- Changed files <=100, target <=80.
- `PLAN.md` status table updated with this concept's PR number, marked `Complete`
  once merged -- this is the last concept in the D4 chain; on completion, Concepts 02
  and 03 (03 also requiring Concept 01.1) become eligible to start.
