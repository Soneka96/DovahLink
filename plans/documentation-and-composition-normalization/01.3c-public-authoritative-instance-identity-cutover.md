## Goal

Implement exactly the public state-authority continuity identity decision from
`01.3a` -- `stateAuthorityId` identifies a continuity epoch of the Host's
authoritative-state store, not an Adapter/Host process instance; it is not a public
counterpart of `adapterInstanceId`, per `01.3a` Section C.
This is an identity-lifecycle contract, not a variable rename -- treat it with the
same rigor `ARCHITECTURE.md`'s "Runtime and identity model" already applies to
`playContextId`/`clientId`/`sessionId`.

## Mandatory invariants to prove

Using the names `01.3a` chose: one identifier represents exactly one documented
authority lifetime; it is stable for that lifetime; it changes exactly at the
documented lifetime boundary; client reconnect does not accidentally create a new
authority identity; a new session does not accidentally create a new authority
identity; a play-context change does not masquerade as a Host restart;
`adapterInstanceId` remains semantically separate; PIDs/ports/paths/sockets are not
used as identity; multi-client sessions observe the same authoritative identity when
attached to the same authority; cache invalidation rejects data from an old
authoritative lifetime; state revision scope matches the canonical protocol document;
`hello_ack`/`state_snapshot`/`state_event` carry the decided value as a required,
non-null field and no other message carries it, per `01.3a` Section C's exact wire-
presence table -- not "every Host-originated message"; a rotation invalidates
incremental continuity from the previous value until a fresh `state_snapshot`
establishes the new baseline, per `01.3a` Section C's post-rotation baseline rule; an
unresolved continuity break stays under its already-rotated value through any number of
failed recovery attempts, rotating again only for a loss detected after a fresh
baseline already exists, per `01.3a` Section C's repeated-loss lock-down; error paths
obey the schema; a startup mint failure fails closed at Host startup, and a runtime
mint failure after a detected continuity break is a fatal Host invariant failure with
no retained/`null` value and no degraded serving, per `01.3a` Section C's two-case
failure-behavior policy.

## Required tests

At minimum, where applicable: same Host process + reconnect -> same
state-authority ID; same Host process + new authenticated session -> same
state-authority ID; same Host process + multiple concurrent clients -> same
state-authority ID; Host restart -> different state-authority ID, rotated at
startup; Adapter/IPC connection loss detected -> different state-authority ID
rotated at the moment loss is observed, *before* any resync/rebind attempt
begins; that same continuity break resolving via the same `adapterInstanceId`
reconnecting -> no further rotation (the state-authority ID from the
loss-detection moment persists into the fresh baseline); that same continuity
break resolving via a new `adapterInstanceId` binding instead -> also no
further rotation, even though `adapterInstanceId` itself changed (per `01.3a`
Section C's continuity-epoch invariant: one break, one rotation, at detection --
neither the pre-redefinition "rotates with `adapterInstanceId`" wording nor a naive
"rotate again when resync succeeds" implementation would pass this test); **repeated
loss before a baseline exists** -- a continuity break rotates the value once (`A ->
loss -> B`), and any number of further failed reconnect/resync attempts, or additional
Adapter/IPC drops, observed *before* a fresh baseline is ever successfully established
under `B`, must not rotate it again -- only a loss detected *after* a baseline already
exists under the current value may produce `C`; a naive implementation that mints a new
value on every detected drop, regardless of whether the prior break was ever
baselined, must fail this test; **runtime mint failure** -- if minting a new value
fails after a continuity break is detected (as opposed to at Host startup, which has
its own existing fail-closed startup test), the Host must not retain the prior
(now-invalid) value, must not substitute or emit `null`, must not continue
`state_snapshot`/`state_event` publication or admission under any value, and must
proceed to its normal deterministic shutdown -- per `01.3a` Section C's failure-behavior
decision; play-context
change -> state-authority ID unchanged, `playContextId` changes; cache holding
`(oldAuthorityId, old/newPlayContext, ...)` is rejected per the `01.3a` contract;
Adapter identity cannot be substituted for public authority identity; envelope
encode/decode across Host <-> SDK preserves the exact field; stale-state/recovery
tests use the new identity tuple; no residual active `bridgeInstanceId` contract use
remains unless `01.3a` explicitly retained it. Do not write tests that merely assert
a renamed string -- test lifecycle semantics.

## PR-size gate

The pre-decision `~75-90` estimate above is a superseded historical planning-time
estimate. Measured direct-hit baseline (`01.3a`'s re-run inventory across
`protocol/fixtures/**`, `sdk/dart/**`, `host/**`, `app/**`, `integration/**`):
**74 files**, plus documentation/tooling files. This is close to the 80-file re-plan
threshold, not comfortably under it -- re-run the exact predicted changed-file
inventory before implementation.
Hard stop: 100. Re-plan threshold: >80.

This is the concept in the D4 chain most likely to approach the limit, because
`bridgeInstanceId` is one field in the shared envelope header present on nearly every
message -- there is no way to rename it across only some fixtures/consumers without a
window where some messages use the old field name and some use the new one
simultaneously on the wire. That is not a safe split; it is exactly the broken
intermediate state D4 forbids. Do not split this migration by fixture or message
family. Apply this tiered policy instead, based on the `01.3a`-informed re-run
inventory:

```text
<=80 predicted files:  normal PR.
81-100 predicted files: stop for maintainer review before implementation. The
    maintainer may explicitly approve one large atomic PR if that is safer than
    introducing an intermediate protocol state.
>100 predicted files:  do not implement. Return to 01.3a and design a genuinely
    coherent staged migration whose intermediate state is itself valid, or stop
    for maintainer direction.
```

Never introduce dual fields, aliases, or compatibility shims unless explicitly
approved as part of the `01.3a` design. This same principle -- never split one
atomic protocol-contract change merely to satisfy a file-count target -- applies
throughout the D4 programme, not only here.

**Re-run inventory before implementation:** 73 files in the core implementation
directories (`protocol/fixtures/**`, `sdk/dart/**`, `host/**`) -- consistent with
`01.3a`'s 74-file estimate -- plus 7 mechanically-required doc/tooling/Adapter-test
files and 6 live-prose-consistency files (`roadmap/02`/`roadmap/03` among them, since
`tooling/test_repository_consistency.py` pins exact wording from both against the old
field name): **86 predicted files**, landing in the 81-100 "stop for maintainer
review" band, not "comfortably under 80." The maintainer explicitly approved
proceeding as one atomic PR rather than any split, per this section's own escape hatch
and `01.3a` Section E's ban on splitting one wire-contract change across PRs.

**Final count:** **99 files** changed on this branch vs. `main`, still under the
100-file hard stop. The gap from the 86-file prediction is almost entirely test-file
fallout the inventory could not fully enumerate in advance (for example
`PublicWebSocketConnectionTests.cs`, `ClientMessageDispatcherTests.cs`,
`dovahlink_client_test.dart`, and the `Fixtures`/fixture-builder files across both
test suites) plus this plan package's own normal bookkeeping overhead (`PLAN.md`,
`CONTEXT.md`, `DIVERGENCES.md`), not additional wire-contract scope.

## Completion criteria and evidence

- `01.3a`'s identity decision is implemented exactly: `StateAuthorityLifecycle` mints
  at Host startup (fail-closed on mint failure), rotates exactly once when
  `IAdapterAvailabilityTracker.AvailabilityChanged` reports a continuity loss, stays
  locked through repeated failed recovery until `Resynchronized` fires a fresh
  baseline, and treats a runtime mint failure as fatal (drives Host shutdown via
  `Program.cs`'s `shutdown.Cancel()` wiring). `PublicEnvelopeCodec` stamps
  `stateAuthorityId` on `hello_ack`/`state_snapshot`/`state_event` only and omits it
  from every other message, matching `01.3a`'s exact wire-presence table -- proven by
  lifecycle-semantics tests (repeated-loss lock-down, post-baseline re-rotation,
