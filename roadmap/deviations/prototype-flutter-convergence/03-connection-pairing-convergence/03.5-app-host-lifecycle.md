# 03.5 — App Host Lifecycle Integration

**Status:** Paused / requires re-planning

## Outcome

The original goal was for Flutter to reflect actual SDK/Host lifecycle rather than prototype or
fabricated state. This convergence step is not claimed complete.

## Why it exists

Connection cards and handoff are truthful only when their status comes from the real discovery,
connection, pairing, and session lifecycle.

## Scope

Original UI intents included showing discovery, availability, connecting, pairing, connected,
reconnecting, unavailable/offline, and repair/re-pair-required conditions where supported by actual
SDK/domain state.

## Non-goals

- This record does not define a new connection or pairing state machine.
- The UI must not invent connectivity, trust, or pairing completion.

## Dependencies / authority

Use current SDK lifecycle and security contracts. See [Stage 5 — Dart Client SDK Foundation](../../../05-dart-client-sdk-foundation.md)
and the [identity and transport security architecture](../../../../ai/context/security/identity-and-transport.md).

## Acceptance criteria

**Original intent, not a current implementation contract:** production Flutter reflects authoritative
SDK/domain states and does not replace them with presentation-only flags.

## History

This step followed the prototype-to-real-connection direction and preceded the later connection-card
handoff audit.

## Current disposition

Paused / requires re-planning against current SDK lifecycle contracts.

## Next action

Define the UI mapping only after the authoritative lifecycle and security states are confirmed.
