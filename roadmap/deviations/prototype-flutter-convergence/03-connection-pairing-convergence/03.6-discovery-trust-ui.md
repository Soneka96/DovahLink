# 03.6 — Discovery / Trust UI

**Status:** Paused / requires re-planning

## Outcome

The original goal was to connect real Host discovery and Known Host metadata to prototype-equivalent
connection UI. This UI convergence step is not claimed complete.

## Why it exists

The prototype needs selectable Host candidates and meaningful known/available states, while discovery
and trust remain distinct application concepts.

## Scope

Present candidates from SDK discovery and relevant Known Host metadata in the connection surface.
The still-valid rule is **discovery candidate ≠ trusted Host**.

## Non-goals

- No LAN or mDNS discovery is implied by this UI plan.
- A candidate, matching name, or endpoint does not create trust.

## Dependencies / authority

Discovery and Known Host semantics remain in the SDK and the
[identity and transport security architecture](../../../../ai/context/security/identity-and-transport.md).
The current local discovery behavior is described in
[03.2](03.2-sdk-local-host-discovery.md).

## Acceptance criteria

**Original intent, not a current implementation contract:** the UI may present candidates and saved
metadata, but trust and verified identity come only from approved connection/security semantics.

## History

This UI slice depended on the completed local discovery and Known Host persistence work, then paused
after the security issue exposed by PR #100.

## Current disposition

Paused / requires re-planning. No LAN trust behavior was implemented by this step.

## Next action

Re-plan candidate and known-host presentation against current SDK APIs and security rules.
