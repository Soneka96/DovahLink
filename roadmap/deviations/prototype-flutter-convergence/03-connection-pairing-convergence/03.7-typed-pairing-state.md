# 03.7 — Typed Pairing State

**Status:** Paused / requires re-planning

## Outcome

The original goal was to replace ad-hoc booleans and strings with reusable typed SDK/domain pairing
state. The security investigation changed the target boundary, so this step is not implemented or
specified for runtime.

## Why it exists

Pairing UI should represent authoritative reusable domain state, not maintain a competing Flutter
pairing authority.

## Scope

The selected DovahLink direction separates bootstrap/security evidence from application
authorization: evidence feeds a pending decision for one exact attempt; Skyrim chooses Pair, Reject,
or Block; durable trust may follow only Pair. Runtime implementation remains deferred.

## Non-goals

- Do not invent a future wire protocol, SAS behavior, or final state model here.
- Do not treat the authorization boundary as implemented.

## Dependencies / authority

Re-plan against the selected direction in the
[identity and transport security architecture](../../../../ai/context/security/identity-and-transport.md)
and the separate [initial-pairing security deviation](../../initial-pairing-security/README.md).

## Acceptance criteria

**Original intent, superseded pending re-planning:** pairing state should be typed and reusable, with
the proof/authorization distinction preserved and one exact attempt identified.

## History

The original typed-state intent predated the S2.2 STOP and the selected DovahLink pending-approval
architecture.

## Current disposition

Paused / requires re-planning. No runtime PendingPairingApproval is implemented.

## Next action

Re-plan the typed state against the current security architecture and the external generic SAS work;
do not define protocol details in this convergence record.
