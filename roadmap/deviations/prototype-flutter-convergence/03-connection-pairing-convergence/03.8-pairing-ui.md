# 03.8 — Pairing UI

**Status:** Paused / requires re-planning

## Outcome

The original goal was to implement the prototype's pairing interaction in production Flutter. This
step is not claimed complete under the future production security architecture.

## Why it exists

The app needs clear pairing status and user guidance without presenting a false success or a pairing
result for the wrong Host/Client attempt.

## Scope

Preserve the product intent for clear waiting/confirmation, rejection/failure, and recovery states;
correct Host/Client association; and no fabricated pairing success.

## Non-goals

- Do not specify production SAS behavior or UI details for a future SAS ceremony.
- Do not treat historical PIN/bearer assumptions as sufficient for the future production path.

## Dependencies / authority

Generic SAS cryptography belongs to
[`Soneka96/sas-pairing`](https://github.com/Soneka96/sas-pairing). DovahLink owns application pairing
UX and authorization. See the separate
[initial-pairing security deviation](../../initial-pairing-security/README.md) and the
[identity and transport security architecture](../../../../ai/context/security/identity-and-transport.md).

## Acceptance criteria

**Original intent, not a current implementation contract:** pairing presentation is clear, truthful,
and tied to the correct application attempt and authoritative outcome.

## History

The prototype pairing interaction preceded the unresolved initial-pairing security work and is
preserved as product intent, not as a selected production ceremony.

## Current disposition

Paused / requires re-planning.

## Next action

Re-plan the application interaction against the selected authorization boundary. Leave production SAS
behavior unspecified until the generic proof passes its security gate.
