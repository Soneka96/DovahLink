# 03.4 — Companion Device Identity

**Status:** Paused / requires re-planning

## Outcome

The original goal was a product-facing companion identity suitable for Host and pairing surfaces.
The step is not implemented as a converged production feature.

## Why it exists

The prototype presents a recognizable device name, while reusable logical client identity and
security behavior belong outside Flutter presentation.

## Scope

Original intended concepts included the SDK-owned stable `clientId` and a display name with the
fallback direction user override → OS device name → “This device.” The product need for a readable
Client/device identity remains valid.

## Non-goals

- This record does not freeze the final model, persistence shape, wire name, or implementation
  details.
- Flutter must not become authority for logical Client identity or security semantics.

## Dependencies / authority

Re-plan against the current [identity and transport security architecture](../../../../ai/context/security/identity-and-transport.md)
and SDK persistence contract. Presentation override, OS name lookup, and logical identity must retain
their documented ownership.

## Acceptance criteria

**Original intent, not a current implementation contract:** the product can identify the companion
in relevant UI while the SDK remains authority for logical identity and security behavior.

## History

This convergence step was sequenced after local discovery and Known Host persistence. It is distinct
from official Stage 3.1–3.3 roadmap phases.

## Current disposition

Paused after the security deviation changed the surrounding Host/Client identity and pairing
architecture.

## Next action

Re-plan the display identity and fallback behavior against current SDK and security contracts.
