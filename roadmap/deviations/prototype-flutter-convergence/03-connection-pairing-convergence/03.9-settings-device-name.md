## Ownership and semantics

The app owns and locally persists the user's display-name override. The SDK continues to own the
logical `clientId`; the override is presentation metadata, not a security identity. The effective
name resolves as saved override, then OS device name, then `This device`, following the identity
architecture.

Pairing supplies the resolved name through its existing optional `displayName` field. The Pairing UI
does not show a second name field. Saving while a trusted Host session is active uses the SDK's
public `client.connections.renameDevice` operation, which updates only that Host's trust record.
Other Known Hosts are not renamed implicitly. Offline, disconnected, or untrusted sessions receive
no rename request; the locally saved name applies to future pairings.

The app saves the local preference before attempting an active-Host rename. A Host rejection or lost
response never rolls back the saved preference; the UI reports local persistence and the Host
acknowledgement separately. A lost response is unconfirmed, and the SDK request is not retried after
an ambiguous transport failure because the Host mutation advances its security fence.

The name is trimmed. Blank input saves `This device` as the explicit override, matching the
prototype. The production input enforces the Host's 64-byte UTF-8 limit and rejects control
characters. If the override cannot be read at startup, the UI leaves it unavailable and pairing
sends `null`, preserving any existing Host label rather than replacing it with a guessed fallback.

## Middleware mapping

`DeviceIdentityMiddleware.call` routes `DeviceNameSaveRequestedAction` to the documented
`_handleDeviceNameSaveRequested` handler. The handler saves locally first, dispatches the saved
name, then conditionally requests a rename from the one active trusted Host and dispatches the
separate typed result. The switch contains routing only; the handler owns validation outcome,
eligibility, sequencing, and error conversion.

## Non-goals

- Settings does not become a trust or security authority.
- A local name change does not fan out across Known Hosts.
- Pairing does not regain a device-name field.
- The phase does not add Overview, gameplay pages, notifications, discovery, or trust redesign.

## Dependencies and authority

Use the current Flutter and SDK boundaries plus the
[identity and transport security architecture](../../../../ai/context/security/identity-and-transport.md).
The prototype owns presentation and interaction; SDK/Host contracts own identity, trust, pairing,
authorization, and rename outcomes.
