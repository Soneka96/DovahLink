# 03.9 — Settings / Device Name

**Status:** Re-planned — implementation in progress

## Outcome

The original goal was to converge Settings with prototype presentation and provide a companion name
for product-facing identity. This step is not claimed complete.

## Why it exists

The prototype shows the companion as a user-recognizable device, while display preference, OS name
lookup, and reusable Client identity have different owners.

## Resolved ownership and semantics

The app owns the user-selected display-name override and persists it locally. The SDK continues to
own the logical `clientId`; the override is presentation metadata, not a security identity. The
effective name resolves as saved override, then the OS device name, then `This device`, following
the identity architecture.

The app supplies the saved preference through pairing's existing optional `displayName` field.
Saving while a trusted Host session is active also sends the SDK's `renameDevice` operation, which
updates only that Host's trust record. Other Known Hosts are not renamed implicitly and remain
unchanged while offline. Saving without an active trusted session updates only the local preference,
which is used by future pairing.

The local preference is committed before an online Host rename is attempted. A rejection or lost
response does not roll it back; the UI keeps the Host acknowledgement separate from the saved
local name, and marks a lost response unconfirmed rather than renamed.

The name is trimmed, and an empty value saves `This device` as the explicit override, matching the
prototype. With no saved override, Settings shows the OS device name when available; this differs
from the prototype's first-run fallback and follows the identity architecture. The Host's existing
64-byte UTF-8 limit and control-character validation remain authoritative. A rename request is not
retried after an ambiguous transport failure because the Host persists the trust mutation and
advances its security fence.

If the override cannot be read at startup, the app keeps the name unavailable and sends `null`
during pairing. This preserves an existing Host label instead of replacing it with a guessed
fallback. Settings can report the load failure and allow another save attempt.

## Non-goals

- Settings must not make Flutter a security or trust authority.
- The prototype's 64 UTF-16-code-unit input limit cannot replace the Host's 64-byte UTF-8 bound for
  non-ASCII names; the production input must enforce the Host constraint.
- This record does not freeze the final Settings layout or interaction details.

## Dependencies / authority

Use the current Flutter and SDK boundaries plus the
[identity and transport security architecture](../../../../ai/context/security/identity-and-transport.md).

## Acceptance criteria

The acceptance criteria are: the app persists only the override; the effective-name fallback follows
the documented override → OS name → `This device` order; pairing supplies that effective name; and a
runtime rename updates only the active trusted Host.

## History

Device-name behavior was part of the prototype convergence sequence after pairing and connection
surfaces were being integrated.

## Current disposition

The ownership and cross-Host behavior are resolved for the Settings / device-identity convergence
phase. Implementation and prototype comparison are in progress; this record does not claim the
phase complete.
